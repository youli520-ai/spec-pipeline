# spec-pipeline

**AI agent 开发的轻量流程治理：文件夹状态机 + 机器硬闸 + 事后审计。**

> When AI agents write most of your code, the bottleneck is no longer typing —
> it's making sure the right things get done in the right order, and that you
> can still trust the result. This is a ~700-line, zero-dependency control
> plane for that problem.

单一操作者（owner）+ 多 AI agent 的本地开发流程。跑在生产环境（无 CI、无远端、
owner 注意力是最稀缺资源）也可以跑在有 CI 的团队里（把落地闸换成你的 PR/CI 即可）。

## 它解决什么问题

用 agent 做主力开发的四个现实：

1. **agent 会跳步**——图省事、自审自执行、verify 写形容词、跳过复核直接归档。
2. **多会话并行同一工作树**——是常态不是例外，互相踩踏、误提交别人的文件。
3. **上下文会丢**——会话被压缩、换模型、换机器，任何依赖「agent 记得规矩」的流程都是纸糊的。
4. **人的注意力最稀缺**——流程成本过高会被 owner 自己抛弃，仪式感不是护栏。

业界的 spec-kit / OpenSpec / BMAD / claude-task-master 都在做「给 agent 的 spec 工具」；
这套做的是**给操作者的流程治理**——不关心 spec 长得多漂亮，关心「跳步这件事会不会被机器拦住」。

## 核心机制：五阶段文件夹状态机

```
00-方案 →(审核)→ 01-下派 →(执行)→ 02-完成 →(复核)→ 03-落地 →(落地+回填)→ 99-归档
                        ↑______ 复核不通过：附驳回意见退回 ______|
```

- 一个方案 = 一张卡（子文件夹，脚本生成五件套骨架）：`spec`（方案）/ `review`（审核意见）/
  `verify`（执行自验，只认数字）/ `recheck`（复核回执）/ `log`（状态流水，含会话指纹）。
- 审核与复核必须是**独立上下文**（新会话或子代理），与执行者互查；下派串行（一次一张卡）。
- 驳回 2 次封顶 → `blocked/` 等 owner 裁决；**准入只有 owner 放行**（agent 无权建卡）。
- 转移图有合法边：跳阶段、终态复活一律机器拒绝；驳回只走 `ret` 别名（保封顶计数）。

## 快速上手

```bash
# 1. 把 pipeline_ctl.mjs 放进你的仓库 scripts/ 目录（唯一依赖：node + git）
node scripts/pipeline_ctl.mjs --help

# 2. owner 放行一个方案后建卡
node scripts/pipeline_ctl.mjs new my-feature

# 3. 随时看全局
node scripts/pipeline_ctl.mjs status      # 存量+缺件+一致性+在途互撞+僵尸卡
node scripts/pipeline_ctl.mjs show my-feature   # 单卡全貌
node scripts/pipeline_ctl.mjs audit       # 当天无卡提交对账（入口纪律抽查）
node scripts/pipeline_ctl.mjs hot web/src/foo.ts  # 改动频率热点（叠补丁信号）
```

卡片数据在 `.pipeline/`（gitignore，owner 的过程资产）；机制 = 脚本 + 内嵌模板（进 git，
换机器 clone 即得）。**模板必须内嵌在脚本里**——放外部目录会在新机器上丢失。

## 八条原则（这套东西的可迁移内核）

| # | 原则 | 一句话 |
| --- | --- | --- |
| 1 | 状态机外化 | 方案生命周期放文件系统，不放对话记忆——上下文会丢，文件不会 |
| 2 | 机器拦动作，人判质量 | 硬闸只查「跳没跳步」（结论填没填/转移合不合法/计数超没超），永不判内容——内容硬门只会造出最快绕过路径 |
| 3 | 规则跟资产走 | checklist 内嵌模板生成到卡上，不依赖 agent 读过任何文档 |
| 4 | 制衡靠上下文隔离 | 审核/执行/复核不同上下文；同上下文自审 = 无效（子代理也算独立，会话指纹可区分） |
| 5 | 失败路径优先设计 | 驳回必带意见、封顶进 blocked 等 owner 裁、回滚=新卡——失败出口比成功路径重要 |
| 6 | 事后可见 > 事前强制 | audit 差集 + log 指纹 + 10 秒抽查，替代 100% 强制——强制做不到的，可见性补 |
| 7 | 入口分级 | 不是所有改动都走全流程；判不准按重的走 |
| 8 | 工具非判据 | 阈值是排序提示不是判据；工具输出事实，人下结论 |

## 机器硬闸清单（拦「跳步」事实，不碰内容）

1. **转移合法性**：合法转移表外一律拒（`00→99` 直达归档、`99→01` 终态复活）；驳回只走 `ret` 别名
2. **结论闸**：`ret`/进 03/进 01/进 02 各自要求对应文件的实际填写内容（防「审核/执行/复核被跳过」）
3. **封顶计数**：第 2 次驳回拒走 ret → 进 `blocked` 等 owner 裁决
4. **slug 全阶段唯一**：含归档卡（重名卡会永久卡死后续移动）
5. **land 主闸**：只能从 03 归档；提交标记缺失只警告不拦（防误伤忘写标记的正常流程）

只报不拦的信号（人下结论）：阶段缺件、判据行数一致性、`hot` 热点、在途卡互撞、
停留 ≥7 天僵尸卡、`audit` 无卡差集。

## 威胁模型与诚实边界

**防**：图省事/自欺的 agent——跳步、忘填、空转、自审自执行。**不防**：恶意攻击者、
内容造假（verify 数字是编的，只有独立重跑能抓——复核强度分级里「重复核」的职责）。

明确承认的边界：

- 入口没有机器闸——「这个改动该不该走流水线」机器判不了（规模/意图是内容判断），
  靠入口纪律 + `audit` 事后抽查兜底。
- 语义重复（改名的重复实现）grep 抓不到——独立上下文带意图搜，降概率不根除。
- 会话指纹理论上可伪造——按需修：真出现一次再上宿主侧交叉验证。
- agent 可以绕过工具直接用文件系统操作卡片——工具不是安全边界，是**让守规矩变成
  最省事路径**的摩擦力设计 + 事后审计的可见性。

## 审核/复核用子代理（省去手动开会话）

实测子代理有独立会话指纹（log 可追溯），独立上下文底线保留。派发 prompt 走固定模板
（读卡 → 按内嵌 checklist 逐条给证据 → 结论落文件并填自己的指纹 → 只审不改 → mv），
不让派发会话自由发挥。折扣：同模型盲区会复现、过程在折叠调用里——**重要方案
（数据链路/发版/安全）仍开独立会话或换模型**。

## 与业界对照

| 业界做法 | 本流水线 | 取舍 |
| --- | --- | --- |
| spec-kit 的 constitution（章程约束） | 原则表 + checklist 内嵌 | 无需新建机制 |
| spec-kit 的 `/analyze` 跨工件一致性 | 判据行数核对 | 弱启发式，只报不拦 |
| OpenSpec 提案先审后行 | 00 准入 + 审核关 | — |
| BMAD 角色化 agent（PM/Architect/QA） | 独立上下文制衡 | 不做角色扮演——「角色提示 ≠ 独立专业」，错误假设会在 persona 间放大 |
| Task Master PRD→任务图 | spec 依赖字段 | 大任务图对单人流水线过重 |
| spec-kit 已知弱点「结构化谎言」（工件齐但内容漂移） | 硬闸只保证动作不保证质量 | 靠 R2 三方一致核对 + owner 抽查，承认边界 |

## 迁移到你的仓库（本地化清单）

直接能用的：状态机、八道硬闸、五件套模板骨架、`status`/`show`/`hot`/`audit`、
封顶与转移语义、子代理审卡用法。

必须本地化的：

| 项 | 本版默认 | 你要改的 |
| --- | --- | --- |
| checklist 条目（C0-C6 / R1-R6） | 通用版 | 加你仓库的红线（如 DOM 层级四态实测、判据三态铁律） |
| `report` 功能域表 | 示例七域 | 对齐你的提交 scope 体系 |
| 落地工具链锚点 | 提示语 | 换成你的 PR review / CI / 部署闸 |
| 卡片数据路径 | `.pipeline/`（gitignore） | 团队场景建议**入库共享**（单人资产模型 → 团队共享模型的语义反转） |
| 封顶次数 / 热点阈值 / 停留天数 | 2 次 / 30 天 3 轮 / 7 天 | 经验值，按节奏调 |
| 会话指纹环境变量 | `CODEBUDDY_SESSION_ID` / `CLAUDE_SESSION_ID` | 加你的宿主注入变量 |

**适用边界**：单人/小团队 + agent 主力开发、CI 轻或无、方案级工作占比高。
不适用：大团队 + 完整 DevOps（PR review 已承担审核复核，再叠一层是过度工程）；
强合规环境（这套太轻，trace 不够）。

从 [HermesWebUI]（自托管 AI 工作台，单 owner + 多 agent 并行开发）的实战流程提炼，
